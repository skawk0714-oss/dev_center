## 2. 응답 규칙
- 항상 **한국어**로 답한다.
- 작업이 끝나면 "무엇을, 어느 파일에서, 왜" 바꿨는지 3~5줄로 요약한다.
- 코딩 초보자를 위해 전문용어는 짧게 풀어서 설명한다.

## 3. 작업 규칙
- 작업을 시작하기 전에 **반드시 `CURRENT_TASK.md`를 먼저 읽고**, 그 "작업 범위" 안에서만 작업한다.
- **기존 파일과 기존 기능을 임의로 삭제하지 않는다.**
- 한 번에 여러 기능을 건드리지 않는다.
- 프로젝트 구조를 알아야 하면 `ARCHITECTURE.md`를 읽는다.
- 구현이 끝나면 요청 기능과 직접 관련된 변경만 남았는지 확인한다.
- 다른 프로젝트 폴더는 건드리지 않는다.

## 3-1. 유지보수 우선 원칙
모든 개발은 유지보수하기 쉽게 만든다.
새 기능을 빠르게 붙이는 것보다, 나중에 찾고 고치고 확장하기 쉬운 구조를 우선한다.

- 중복 코드는 가능하면 공통 함수/공통 include/공통 컴포넌트로 정리한다.
- 메뉴, 네비게이션, 버튼, 데이터 스키마처럼 반복되는 구조는 한 곳에서 관리되도록 만든다.
- 기능을 추가할 때 기존 구조와 역할을 먼저 확인한다.
- 단, 유지보수 목적의 정리(리팩터링)는 현재 요청 범위 안에서만 허용한다.
  범위 밖 정리는 별도 작업으로 분리하고 사용자 승인을 받는다.

## 4. 보안 규칙 (예외 없음)
- `.env` / `config` 파일의 민감정보를 코드나 답변에 그대로 출력하지 않는다.
- 사용자가 입력한 값은 검증·이스케이프한 뒤 사용한다.

## 5. 완료 전 검증 규칙
- "완료"라고 말하기 전에 실제로 검증 명령을 실행하고 통과한 명령을 답변에 적는다.
- PHP 파일을 수정했으면 반드시 `php -l 파일명`을 실행한다.
- 검증하지 못한 항목은 "검증 못함"이라고 명확히 말하고 완료 처리하지 않는다.

## 6. 반드시 사용자 승인을 받아야 하는 작업
- 파일/폴더 **삭제**
- 로그인·인증 구조 변경
- 전체 디자인/레이아웃 대규모 변경
- 한 번에 5개 이상 파일을 바꾸는 작업
- 외부 라이브러리 새로 설치

## 7. 커밋 규칙
- 커밋 전 `php -l` (또는 해당 언어 문법 검사)를 반드시 통과한다.
- 커밋 메시지는 `feat:` / `fix:` / `style:` / `docs:` 접두사를 사용한다.
- 요청 기능과 직접 관련된 변경만 한 커밋에 담는다.
- 포맷·들여쓰기만 바뀐 변경은 커밋하지 않는다.
